Center diagram proposals

Three static sketches of the main diagram, all in the same frame. The story text is on the left, with one callout from the active text line into the diagram. Charts are on the right, with thin leader lines to what they measure. All three show the same moment: step 4 of a “follow a batch” walkthrough, where our batch reaches the introducer.

All three use fixed geometry. In-memory segments, file segments and files go into fixed slots, so nothing reflows or shifts as counts change. Animation would only change fills and states in place.

Callout grammar

  • Story callout (accent color, one at a time): it runs under the highlighted phrase to the edge of the text column, then a diagonal, then a horizontal run into its target.
  • Chart leaders (thin and gray, always present): a short horizontal out of the chart, a diagonal, then a horizontal into the thing the chart measures.

A possible “follow a batch” walkthrough

  1. KV sends a DCP snapshot. The mutations land in the 20MB flow-control buffer.
  2. The DCP goroutine calls batch.Index() for each doc into the vbucket’s batch, and hands it off at 200 ops or at the end of the snapshot.
  3. A batch worker receives it over its capacity-1 channel. It merges in other batches until it has 200 ops or its 100ms ticker fires.
  4. The herder gate. The batch passes the app herder’s memory check. Today it doesn’t block.
  5. Scorch.Batch() analyzes the docs on the analysis queue and builds one in-memory segment.
  6. The introducer makes a new root snapshot with our segment, at epoch N. Our docs are now searchable, and Batch() returns (unsafe_batch).
  7. The persister naps, then in-memory merges our segment with its neighbors into a zap file, fsyncs it, swaps it into the root, and commits root.bolt.
  8. The merger later merges that file into a bigger one. Our docs move again, and the old files become garbage.
  9. Cleanup deletes the old files once no root.bolt snapshot lists them. Our batch is now part of a big, durable segment.

The scenarios (slow disk, huge ingest, slow query) would come after this, as separate chapters on the same diagram.

A · The spine

One vertical pipeline of goroutines, in the order data meets them. Data containers sit inline: the DCP buffer, worker channels, the root snapshot, and the index directory. A dashed line splits memory from disk. Dotted lines on both sides show that the persister’s and merger’s results go back through the introducer.

Good at

  • Reads like the code path. Each box is a real goroutine or function, in call order.
  • Following one batch is a straight walk down the page. Each step’s callout target sits a bit lower than the last.
  • The memory/disk boundary is explicit, and the herder shows up as a gate across the flow.
  • The return-to-introducer loops make “one goroutine owns the root” visible.

Weaker at

  • It’s tall. Everything fits at 900px, but there’s little room to spare.
  • The persister and merger sit side by side under the root, so their pacing of each other (watchers, nap breaks) needs extra drawing to show.
  • Without a time axis, it shows state. Scenarios that are about timing, like naps or slow fsyncs, rely on the charts.

B · Shelves and movers

Data at rest is a stack of horizontal “shelves”: unacked DCP bytes, batches in flight, in-memory segments, file segments, the directory, and queries. Goroutines are the “motors” on the conveyors between shelves, each moving data one shelf down.

Good at

  • Puts the emphasis on where the data is, which is what most support questions are about: memory growth, file counts, disk usage.
  • Each goroutine’s job is clear from its position: it moves data from one shelf to the next.
  • Shelves are wide, fixed rows of slots, which suits counters and fill levels and stays very calm when animated.
  • Backpressure has a simple visual: an upstream shelf fills while the motor below it is stalled.

Weaker at

  • It hides the call structure. Workers, Scorch.Batch() and the analysis queue are folded into one “introducer” conveyor.
  • The merger doesn’t fit the downward flow, since it moves file segments back into the same shelf.
  • More abstract, and so further from the code that the readers know.

C · Rows with time traces

Still top-down, but each goroutine (and the two big data structures) is a row with a scrolling trace of the last 10 seconds, like a logic analyzer or Go’s execution tracer. A batch’s journey is drawn as a line hopping across rows.

Good at

  • The best fit for timing stories: naps, fsync stalls, blocking, and the merger breaking the persister’s nap are all visible as shapes over time.
  • “Follow a batch” becomes a literal line across rows, like a distributed trace.
  • Will feel familiar to anyone who has used go tool trace.

Weaker at

  • Constant leftward scrolling is motion, even if it’s slow and steady. That’s the opposite of the calm you asked for, unless it advances only per step.
  • Shows little about the shape of the data: individual segments, files, root.bolt.
  • The data rows partly duplicate the right-hand charts.
